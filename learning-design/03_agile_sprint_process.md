# 03 · Agile Sprint Process for Learning Design

## Why Agile in Learning Design?

Traditional instructional design models (like ADDIE) are linear and phase-gated — you finish analysis before design, design before development, and so on. This works well for stable, well-defined projects but struggles when requirements evolve, feedback loops are slow, or stakeholders need to see progress early.

**Agile addresses this by:**
- Breaking work into short, iterative cycles (sprints)
- Producing working drafts early and often
- Building feedback into the process rather than reserving it for the end
- Allowing the design to evolve based on what you learn along the way

> Agile doesn't replace good instructional design thinking — it changes *when* and *how* that thinking is applied.

---

## Core Agile Concepts for LXDs

| Concept | What It Means in Learning Design |
|---|---|
| **Sprint** | A fixed time period (1–2 weeks) in which a defined set of design tasks is completed |
| **Backlog** | The prioritised list of all work to be done across the project |
| **Sprint Backlog** | The subset of backlog items selected for the current sprint |
| **Increment** | The working output produced at the end of each sprint (e.g., a completed module draft) |
| **Velocity** | How much work the team can reliably complete per sprint |
| **Retrospective** | End-of-sprint reflection on what worked and what to improve |
| **Review / Demo** | End-of-sprint walkthrough of the increment with stakeholders |
| **Product Owner** | In ID context: the SME or faculty member who sets priorities and approves content |
| **Scrum Master / Facilitator** | In ID context: typically the LXD — keeps the process running and removes blockers |

## Agile Frameworks Compared

### Scrum
Best for: Defined project timelines with clear milestones and a dedicated team.

- Work is organised into **2-week sprints**
- Each sprint has a **planning session**, **daily check-ins** (or async updates), a **review**, and a **retrospective**
- Roles are defined: Product Owner (SME/faculty), Scrum Facilitator (LXD), Team
- Output at end of each sprint: a **reviewable increment** of the course

### Kanban
Best for: Ongoing work, maintenance projects, or teams with unpredictable demands.

- Work items flow through columns: **To Do → In Progress → In Review → Done**
- No fixed sprints — work is pulled when capacity is available
- Focus on limiting work in progress (WIP limits) to avoid bottlenecks
- Great for managing backlog items across multiple simultaneous projects

### SAM (Successive Approximation Model)
Best for: Higher ed and corporate learning design; blends Agile with familiar ID structure.

- **SAM1:** For smaller, simpler projects — rapid prototyping → feedback → revise → release
- **SAM2:** For larger projects — three phases: Preparation → Iterative Design → Iterative Development
- Emphasises **getting something in front of stakeholders quickly** rather than perfecting before sharing

## A Typical Sprint in Learning Design

### Sprint Planning (Day 1, ~1 hour)
- Review the backlog with the team
- Identify which items are ready to work on (have clear requirements, dependencies resolved)
- Select items for this sprint based on priority and capacity
- Define the **sprint goal** — one sentence that captures what will be achieved

**Sprint Goal Example:**
> *"By end of sprint, Module 2 content will be drafted and ready for SME review."*

### Daily or Weekly Check-in (5–15 min async or sync)
- What did I complete since last check-in?
- What am I working on next?
- Is anything blocking me?

### Sprint Review / Demo (Last day, ~30–45 min with SME)
- Walk through the increment (module draft, storyboard section, assessment design)
- SME or stakeholder gives structured feedback
- Note: this is a **review**, not an approval gate — feedback informs the next sprint

### Sprint Retrospective (Last day, ~30 min, team only)
- What went well this sprint?
- What could be improved?
- What will we do differently next sprint?

**Retrospective formats:**
- **Start / Stop / Continue** — simple and quick
- **4Ls** — Liked, Learned, Lacked, Longed for
- **Rose / Thorn / Bud** — positive, negative, potential

## Running the Backlog

The backlog is the heart of Agile project management. Every task, decision, open question, and future idea lives here.

### Backlog Item Structure

```
Title: [Short descriptive name]
Description: [What needs to be done and why]
Acceptance criteria: [How will we know this is done?]
Priority: High / Medium / Low
Status: To Do / In Progress / In Review / Done
Assigned to: [Name]
Sprint: [Which sprint this is planned for]
Notes: [Dependencies, blockers, context]
```

### Backlog Grooming (Weekly, ~30 min)
- Add new items that have emerged
- Refine descriptions and acceptance criteria on upcoming items
- Re-prioritise based on what's been learned
- Move items between sprints as needed
- Archive completed items

### Backlog Zones
| Zone | Description |
|---|---|
| **Sprint Backlog** | Items committed to the current sprint |
| **Ready Queue** | Refined items ready to be pulled into a sprint |
| **Backlog** | All other items; not yet refined or prioritised |
| **Icebox** | Ideas or items deferred indefinitely |
| **Done** | Completed and accepted items |

## Agile Principles Applied to Learning Design

From the Agile Manifesto, adapted for ID practice:

| Agile Value | What This Looks Like for LXDs |
|---|---|
| **Individuals and interactions** over processes and tools | Prioritise the SME relationship and real conversations over bureaucratic check-ins |
| **Working software** over comprehensive documentation | Prioritise reviewable course drafts over perfect design documents |
| **Customer collaboration** over contract negotiation | Keep the SME involved throughout, not just at sign-off moments |
| **Responding to change** over following a plan | Be willing to revisit earlier decisions when new information emerges |

---

## When to Use Which Approach

| Situation | Recommended Approach |
|---|---|
| New course build, dedicated team, clear deadline | Scrum with 2-week sprints |
| Ongoing course maintenance across multiple projects | Kanban |
| Small course revision or single component redesign | SAM1 (rapid prototype → review → revise) |
| Large, complex course with multiple modules and stakeholders | SAM2 or Scrum |
| Exploratory project with unclear requirements | Kanban or lean sprint approach; clarify before committing |

---

## Common Agile Pitfalls in Learning Design

- **Skipping retrospectives** — teams under pressure skip reflection, which means the same problems recur sprint after sprint
- **Treating the sprint plan as fixed** — the plan is a commitment to try, not a contract; adjust if circumstances change
- **Backlog neglect** — a stale, unprioritised backlog creates confusion and slows the team
- **SME overwhelm** — involving the SME in every daily check-in burns them out; protect their time and focus their involvement on reviews
- **Mistaking iteration for rework** — iteration is planned refinement; rework is what happens when you didn't gather enough information upfront
